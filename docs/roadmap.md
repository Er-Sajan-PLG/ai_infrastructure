## Phase 1 queue

Priority order per charter §24 (dependency + verifiability first). Sources: [`../TAXONOMY.md`](../TAXONOMY.md) §4.

1. `tool-registry` (tools) — no dependencies, consumed by almost everything.
2. `model-provider-abstraction` (models) — no dependencies, consumed by everything above.
3. `react-agent-loop` (agents) — depends on 1+2; first end-to-end composition.
4. `execution-trace-recorder` (observability) — enables honest evaluation of 3.
5. `vector-memory-store` (memory), then `basic-rag-pipeline` (retrieval) — depends on 2/5.
6. `mcp-client` (mcp) — COMPATIBILITY candidate; narrow stdio client.

For each: RESEARCHED → UNDERSTOOD → DECIDED (ADR) → DESIGNED → IMPLEMENTED → TESTED — one stage at a time, no skipping (charter §4).

## What's deliberately NOT in Phase 1

- The study pipeline itself (Phase 2 machinery).
- Distributed/durable execution, GPU/deployment infrastructure, fine-tuning.
- Any external-service dependency (vector DBs, hosted eval platforms) — out of scope.

- **Session 15 (audit follow-up — `AI-003` closed, the audit's only genuinely unmet security rule):** The 2026-09-16 audit found least privilege **MISSING**, not inapplicable: `grep` for `allowlist|permitted|deny` across the loop returned nothing, `RegistryDispatcher.schemas()` advertised **every** registered tool with no filter, and `run()` had no `tools=` parameter. - **Session 16 (`mcp-client` → RESEARCHED):** Capability 5 of 7, and the first whose subject is **another system's protocol** rather than a boundary we define. Four sources studied against primary material — the MCP specification itself, both official SDKs, and an independent Go client. Three new registry entries plus a re-review note on the session-6 MCP entry (21 total). Taxonomy → `RESEARCHED`.
- **THE HEADLINE, and it corrected the premise this session was launched with.** The current MCP revision is `2026-07-28`, not `2025-06-18`. It **deleted the `initialize` handshake**: *"Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now carries its protocol version and client capabilities in `_meta`."* The spec now names two eras — **Modern** (per-request `_meta`, `2026-07-28`+) and **Legacy** (`initialize` handshake, `2025-11-25` and earlier) — and its compatibility matrix says a modern client against a legacy server **fails** rather than degrades. So the era choice determines which servers a client can reach at all. **This is the ADR's first decision, not a detail.** The survey prompt asserted the stale revision; the README and schema directory listing contradicted it within two fetches. Same failure class as the OTel "this page has moved" trap: the thing that was true when the question was written is not evidence it is true now.
- **What is stable across both eras, and therefore the safe place to start:** the stdio framing rule is byte-identical (`Messages are delimited by newlines, and MUST NOT contain embedded newlines`), as are the JSON-RPC 2.0 base, the `tools/list` + `tools/call` shapes, the `Tool` descriptor, the five content-block types, the `isError` semantics, and the two-Warning security posture. The framing module's correctness does not depend on the era decision.
- **The spec does NOT say what a client does with non-protocol stdout** — a genuine gap, verified by reading both eras' transport pages in full. Only the server-side prohibition exists. All three surveyed clients therefore chose differently: the Python SDK logs and **stays connected**, the Go client silently discards, the TypeScript client **closes the transport**. Three implementations, three answers, none contradicting the standard. We must choose and document.
- **The error taxonomy converged with our own, on the same axis and for the same reason.** MCP splits protocol errors from tool-execution errors by *who can fix it* — *"Protocol Errors indicate issues with the request structure itself that models are less likely to be able to fix"* vs *"Tool Execution Errors contain actionable feedback that language models can use to self-correct."* That is exactly ADR-0006 D-4's model-actionability axis. **One genuine mismatch:** MCP files *invalid arguments* as a protocol error while our `INVALID_ARGUMENTS` is model-visible. Recorded as an open question, not smoothed over.
- **The dependency posture is decisive, and only one reference survives it.** The Python SDK needs `anyio` (plus `pydantic`, `httpx2`, `jsonschema`, `opentelemetry-api`, …) and is async-only; the TypeScript SDK's stdio entry point requires `cross-spawn`. **`mark3labs/mcp-go` is the only surveyed stdio transport written on the standard library alone**, and is the primary structural reference. Adopting either official SDK would require an ADR under charter §22.
- **Two failure modes worth recording because a naive implementation gets them wrong *silently*.** (1) The Go client drains stderr continuously into a **64 KiB drop-oldest ring** — *"the transport drains stderr continuously so that the OS pipe (about 64KB) can never fill up and block the child process, which would deadlock the whole stdio channel."* (2) The Python SDK kills the whole POSIX process **group** via `os.killpg`, which *"reaches every descendant atomically, even ones whose parent already exited"* — neither the Go nor the TypeScript client does this, so both leak grandchildren. Neither bug shows up on a cooperative server.
- **No client implementation uses a shell.** All three pass an argv array; TypeScript states `shell: false` explicitly. Worth matching deliberately and pinning with a test that a `;` in a config value is passed literally.
- **`AI-010` lands here and does not carry over.** `react-agent-loop`'s README declares approval gates a non-goal, and the 2026-09-16 audit adjudicated that a legitimate DEFER. But MCP's own tools page carries a `<Warning>`: *"there SHOULD always be a human in the loop with the ability to deny tool invocations."* A declared non-goal for a loop that dispatches in-process does not extend to a client dispatching to **processes we did not write**. Phase 1 need not ship an approval UI — the spec says "applications SHOULD" — but the seam must exist, or the capability contradicts the protocol it implements.
- **`inputSchema` loosening is a direct hit on `tool-registry`.** `2026-07-28` allows any JSON Schema 2020-12 keyword (`oneOf`, `$ref`, `if`/`then`/`else`, `$defs`), and the spec states clients **MUST** support 2020-12 for schemas without an explicit `$schema`. Our registry implements a documented *subset* and rejects unknown keywords loudly (ADR-0006 D-2). Same shape as the `mappingproxy` boundary defect — two components correct in isolation, undefined at their seam — except this boundary is external, so it cannot be fixed by relaxing our own rule. **Two of the spec's security constraints independently validate choices we already made:** never auto-dereference a network `$ref`, and bound composition-keyword validation against DoS.
- **Session 16, continued (`mcp-client` → DECIDED → DESIGNED → IMPLEMENTED → TESTED):** The research record's open questions were answered and the capability built end to end. `specifications/mcp-client.md`, `docs/decisions/0009-mcp-client.md` (decision: **COMPATIBILITY**), and `catalog/protocols/mcp_client/`. **361 tests pass** (was 317); the entry contributes 44. Taxonomy → `TESTED`, making the lifecycle distribution `DISCOVERED 2 · RESEARCHED 1 · TESTED 4` — the fourth capability, in the fourth category.
- **The ADR's first decision was the era choice, and it went legacy-only.** `2026-07-28` removed the `initialize` handshake; no deployed server completes a modern handshake, so a modern-only client would reach nothing. The taxonomy scopes this as *"a thin working client"*, and a client that cannot connect to a deployed server is not working. Confined to one module: framing, correlation, the error mapping, and the projection are identical in both eras, so the modern path is additive later.
- **`AI-010` is answered by a mandatory approval seam that defaults to DENY.** `MCPClient` consults an `ApprovalPolicy` **before** writing a `tools/call` frame; `approvals=None` becomes `DenyAllApprovals()`, and a caller wanting autonomy writes `AllowAllApprovals()` — a name that reads as the decision it is. A denial is a **model-visible** `ToolFailure` naming the policy, because the model should know its action was refused. This is where the `react-agent-loop` deferral stops carrying: that loop dispatches in-process, to code the caller wrote; this client dispatches to **processes we did not write**, and the protocol's own tools page carries a `<Warning>` that there *"SHOULD always be a human in the loop with the ability to deny tool invocations."*
- **The projection is lossy by design, and the exclusions are named.** A remote tool the registry cannot represent is excluded with a reason from `ProjectionReport.why(name)`, never adapted. - **Default-off content capture is the MINORITY position, and that is the argument for it.** Only **one of six** surveyed systems states a default-off policy — OTel — and it is the only one that has been through a privacy review; OpenInference, MLflow, Langfuse, LangSmith and AgentOps either capture by default and redact afterwards, or say nothing at all. - **`stop_reason` is our field.** `react-agent-loop` already computes `StopReason`, and **none of the six** surveyed systems has a place for *why the run ended*. It is arguably the single most valuable field in a trace, and a `trace_id` with no `trace_end` record is now a representable state — a crash, a kill, a process death — rather than an ambiguity.
- **A tool call and its result are ONE record, unanimously.** OTel puts the result as an attribute on the same span; OpenInference and MLflow carry `tool_call.id` alongside; there is no "tool result" node in any of the six. Splitting them would force a join to answer *"did this call succeed?"*. Implemented as a context manager, so the record is written on `__exit__` — an exception inside the block still produces a record with `outcome="error"`, because a missing record is indistinguishable from a tool never called.
- **The units hazard, and it is real.** Six systems use at least four unit conventions, and **MLflow disagrees with itself within one object** — span times in nanoseconds, trace duration in milliseconds — while Langfuse and AgentOps state no unit at all.
