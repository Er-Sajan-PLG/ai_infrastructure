## Trade-offs and what to avoid

The phase Method makes this step **session** work rather than pipeline work: the pipeline supplies evidence and the session supplies judgement (charter §6). The notes below are therefore derived only from facts measured at the commit above, and each is labelled.

- OBSERVATION: Phidata/Agno's conceptual layering is the most interesting signal — Agents, Teams, Workflows, Agent OS, Knowledge, Memory, Storage, Tools, Models, Reasoning, Evaluation, Observability, Guardrails. This appears to be a real architectural taxonomy, not merely feature folders. The critical question is what relationship the project establishes between them.
- OBSERVATION: `Agent OS` is by far the most interesting clue for JARVIS — `cookbook/05_agent_os/` with subdirs for python_client, os_config, observability, mcp, remote, skills, agentos_tools suggests a system-level execution/control surface around agents. That overlaps strongly with JARVIS's need for an authority/control layer over subordinate agents, tools, models, and environments. Determine what the "OS" abstraction owns vs what an Agent owns vs what a Team owns vs what a Workflow owns.
- OBSERVATION: Memory/session/checkpoint is much stronger evidence than LlamaIndex — `05_state_and_session`, `06_memory_and_learning`, `18_checkpointing`, `21_fork_session` for both agents and teams. Determine whether checkpoint is a snapshot of agent cognition/state or merely conversation persistence — this distinction matters for resumable autonomous execution.
- OBSERVATION: Evaluation is one of the strongest findings — `09_evals/` with accuracy, agent_as_judge, performance, reliability, suite — multiple evaluation dimensions that could inform worker governance. But verify these are framework primitives, not just cookbook examples.
- OBSERVATION: Guardrails finding is stronger than the generic warning — attached to agents (`02_agents/08_guardrails`), teams (`03_teams/18_guardrails`), workflows (`04_workflows/.../guardrails`), and `libs/agno/agno/guardrails`. Determine WHERE policy is enforced — that is the deeper architectural question.
- DESIGN OPINION: For the deep dive, trace source-backed relationships among Agent, Team, Workflow, Agent OS, Skills, Tools, Models, Knowledge, Memory, Sessions, Checkpoints, Guardrails, HITL, Evaluation, Observability, MCP, and remote execution. Determine ownership and boundaries: configuration vs runtime, agent vs orchestrator, memory vs session vs checkpoint, knowledge vs retrieval, tool vs skill, guardrail vs authorization, workflow vs autonomous agent behavior.
- DESIGN OPINION: Phidata/Agno's retrieval/knowledge architecture (`07_knowledge/`, `vector_dbs/`, `custom_retriever/`, `reranker/`) could overlap with STEMMA, but do NOT conflate Agno's knowledge system with STEMMA's canonical knowledge layer. The safe architecture is: STEMMA canonical layer → derived retrieval indexes → Agent knowledge subsystem → Agent.
- DESIGN OPINION: Fallback models (`02_agents/17_fallback_models`, `03_teams/17_fallback_models`) is a better model-provider signal than mere provider folders — investigate whether fallback is based on provider failure, rate limits, context limits, task capability, cost, latency, or explicit configuration. This could inform JARVIS's model router.
- INFERENCE: The pipeline's "Declared dependencies: 0" for a 14-manifest monorepo is a measurement failure, not an architectural fact. Flag dependency evidence as INCOMPLETE rather than letting downstream analysis interpret zero deps as a characteristic. From LlamaIndex + OpenHands + Phidata, the pattern is clear: Phase 1 as cheap non-executing reconnaissance is working, but you need a Phase 2 architectural reconstruction layer that uses Phase 1's findings to selectively read source and establish relationships. The next evolution should produce a common vocabulary: authority → orchestration → execution → capability → state → knowledge → environment → observation.
