## Trade-offs and what to avoid

The phase Method makes this step **session** work rather than pipeline work: the pipeline supplies evidence and the session supplies judgement (charter §6). The notes below are therefore derived only from facts measured at the commit above, and each is labelled.

- OBSERVATION: Pydantic AI is one of the most important repos in this study — not as "another agent framework" but as a potential **execution-contract architecture** with an unusually relevant combination: Agent + explicit graph + model/provider abstraction + tool execution + durable execution (DBOS/Prefect/Temporal) + evaluation. That combination makes it a very useful bridge repository between the architectural questions in Agno/OpenHands and the governance/evidence questions surfaced by Phoenix.
- OBSERVATION: The structural report has not yet demonstrated the architecture — it has only given enough signals to know this repo deserves deep Phase-2 reconstruction. The package decomposition (`pydantic_ai/`, `pydantic_graph/`, `pydantic_evals/`, `durable_exec/{dbos,prefect,temporal}`, `capabilities/`, `common_tools/`) suggests a much richer architecture than the four candidate patterns (agent-loop, evaluation, model-provider, tool-registry) suggest.
- DESIGN OPINION: For the deep dive, prioritize: (1) Agent architecture — what does Agent own vs delegate to model, provider, tool, graph, execution infrastructure? (2) Pydantic Graph — what does it represent? Workflow engine? State machine? Agent execution graph? Generic orchestration primitive? Is execution deterministic, model-driven, or hybrid? (3) Durable execution — investigate `durable_exec/{dbos,prefect,temporal}` — is there a common durable-execution contract? Trace: core execution → durable execution abstraction → backend adapter.
- DESIGN OPINION: Model/provider architecture is probably genuinely important — trace Agent → model abstraction → provider abstraction → provider API. Determine precisely what each layer owns (auth, transport, capabilities, streaming, tool calling, retries, usage metadata). Identify the extension contract for adding a new provider/model. Tools need careful reconstruction: distinguish tool collection vs registry vs schema/declaration vs dispatcher vs executor.
- DESIGN OPINION: `capabilities/` is an un-surfaced architectural concept — determine what "capability" means and how it differs from model, provider, tool, agent, authorization. This is particularly important for your architecture where capability and authority are separate concepts. `common_tools` does not necessarily imply a registry.
- DESIGN OPINION: Pydantic AI could be particularly valuable for your "durable agent" problem — your architecture is moving toward AI reasoning + structured execution + human authority + durability + verification + multiple workers. Pydantic AI appears to have architectural surfaces for all of these. The question is whether they are actually composable architectural layers or simply packages that happen to coexist.
- INFERENCE: The 1,828 test files and unusual YAML/Python distribution (1504 `.yaml`, 802 `.py`) suggest a huge amount of declarative material, fixtures, or configuration data — investigate what those YAML files actually represent. The dependency measurement is broken — `Declared dependencies: 0` for a 5-manifest monorepo is actively misleading; the pipeline should represent dependency evidence status as INCOMPLETE rather than a literal zero. Do not recommend adoption yet — extract architectural patterns, trade-offs, anti-patterns, and unresolved questions first.
